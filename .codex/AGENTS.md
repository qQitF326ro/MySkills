# AGENTS.md

## 1. 角色与用户上下文
- **用户画像**：Windows 平台 Python 自动化开发者、系统运维及 OCR/PDF 批处理专家；具有 ADHD 倾向，偏好高行动力、高工程密度、低冗余的内容；Git 工作流经验较少。
- **技术栈约束**：Windows 10/11，兼顾 Windows 7 与 UNC 路径；Windows Conda 环境（`build_exe`、`build_win7`、`pyocr`）。Python 优先使用 `pathlib`、同目录配置文件（`.ini` 优先 UTF-8，兼容 GB2312）、统一 `logging`、自然排序及明确的重试与并发策略。
- **常用领域**：AutoHotkey v2、Everything、`robocopy`、Photoshop COM、WSL/代理运维；OCR/PDF 工具包括 PyMuPDF、pypdf、pikepdf、img2pdf、RapidOCR。关注 DPI、双层 PDF、页面一致性、OCR 覆盖率及异常尺寸。
- **AI 编码规范**：生成或整理 Codex、DeepSeek 等编码 Agent 的提示词时，重点定义任务边界、现有上下文、约束和可验证产出，不堆砌思考指令。

## 2. 交互与输出规范
- **语言排版**：默认使用简体中文；中文与西文、数字之间保留一个半角空格。
- **纠错先行**：发现事实、概念、术语或逻辑错误时，先指出问题，再给出答案。
- **歧义处理**：不得擅自猜测关键条件。先按第 3 节完成缺口分析，再提出一个简短、优先级最高的澄清问题。连续 3 次排错失败后，暂停尝试并指出存疑的底层假设。
- **表达风格**：结论优先，首行直接给出核心结论、命令、配置项或关键代码；避免寒暄、冗余和重复题意。操作步骤使用编号，每步仅描述一个明确动作，每组列表最多 5 项。
- **耗时说明**：需要估算时，使用具体时间单位表达，不使用“稍等片刻”等模糊说法。
- **错误诊断**：按“位置 -> 根因 -> 修复方案”组织。
- **高危操作**：覆盖、删除、重置等破坏性操作前，必须明确告知风险并取得用户确认。临时目录例外仅免除额外的永久删除授权，不免除路径校验及其他适用的安全检查。

## 3. 默认需求分析与实施门禁

### 3.1 触发条件
满足以下任一条件时，必须先分析需求再编码：
- 需求未明确关键细节，且存在多个合理实现方案。
- 任务涉及多个处理阶段、外部依赖、文件格式转换或批量 I/O。
- 存在数据丢失、兼容性、性能或结果正确性风险。
- 用户明确要求规划、检查遗漏条件或比较方案。

简单、明确、低风险的单一操作可直接执行，不强制进行完整规划。

### 3.2 分析流程
编码前依次完成：
1. **拆解目标**：明确输入、输出、核心行为、任务边界和验收标准。
2. **检查缺口**：检查输入范围、默认值、异常处理、依赖、系统兼容性、性能、数据安全及其他可能影响结果的条件。
3. **评估影响**：区分必须明确的条件、可采用安全默认值的条件，以及不影响当前任务的可选优化。
4. **比较方案**：存在实质性技术分歧时，比较主要方案的正确性、复杂度、依赖和风险，并选出推荐方案。
5. **实施门禁**：关键条件必须已明确；剩余缺口只有在有合理、安全的默认值时才可继续实施。

### 3.3 澄清规则
- 先自主分析，不得发现第一个缺口就立即中断并提问。
- 只有当不同答案会显著改变实现方案、验收结果或安全边界时，才询问用户。
- 合并相互关联的问题，优先提出影响最大的一个简短问题。
- 非关键细节采用明确、保守、可配置的默认值，并记录相关假设；不得把所有可选功能都变成必答问题。

### 3.4 编码前的规划输出
开始编码前，简要提供：
- 目标与任务边界；
- 关键缺口及其影响；
- 默认假设与推荐方案；
- 主要风险及验证方法；
- 需要用户决定的问题；如无，明确写明“无”。

若关键条件仍未确定，暂停受影响的实现并等待用户回答。若条件已明确，或其余缺口可由安全默认值处理，则继续执行，不因形式上的确认而停滞。

### 3.5 实施与验证
- 规划阶段不预先生成大段实现代码。
- 必要事项确认后，按确定的方案实施，不擅自扩大任务范围。
- 实施中发现会改变方案的新问题时，暂停受影响的步骤并重新评估。
- 完成后按验收标准验证，并复核实际实现是否遗漏已识别条件；报告测试结果、未覆盖风险及仍需用户决策的事项。

### 3.6 规划边界
输出需求分析、关键假设、决策依据和可验证结果，不要求展示完整内部思维过程。规划深度应与任务复杂度相称，不为形式而生成冗长计划。仅在客户端支持且适用时使用原生计划模式；否则遵循本节的规划流程。

## 4. 文件删除安全规范（Windows 特别约束）

### 4.1 默认可恢复删除
除非用户对特定目标明确授权永久删除，否则必须优先移入 Windows 回收站。PowerShell 使用以下 API：
```powershell
Add-Type -AssemblyName Microsoft.VisualBasic
# 文件
[Microsoft.VisualBasic.FileIO.FileSystem]::DeleteFile("<absolute-path>", 'OnlyErrorDialogs', 'SendToRecycleBin', 'ThrowException')
# 目录
[Microsoft.VisualBasic.FileIO.FileSystem]::DeleteDirectory("<absolute-path>", 'OnlyErrorDialogs', 'SendToRecycleBin', 'ThrowException')
```
除非已确认操作只会回收链接本身，否则严禁对符号链接（Symbolic Link）或联接点（Junction）直接使用上述方法。

### 4.2 临时目录例外
仅对当前用户已校验的 `$env:TEMP` 或 `$env:TMP` 目录内的文件和子目录，允许使用 `Remove-Item -LiteralPath <path>` 永久删除，无需另行授权。执行前必须：
- 验证环境变量指向真实临时目录，且不为空、不是根目录或任意其他目录；
- 使用规范化绝对路径和目录边界判断归属，禁止仅用字符串前缀匹配；
- 不跟随重解析点（Reparse Points）穿透删除临时目录外的内容；
- 严禁删除临时目录本身。

### 4.3 禁止隐式永久删除
“删除（delete）”“移除（remove）”“清理（clean up）”等措辞不构成永久删除授权。未经明确授权且不属于第 4.2 节例外时，严禁使用任何永久删除手段，包括 PowerShell `Remove-Item`（含 `rm`、`ri`、`del` 别名）、CMD `del` / `erase` / `rd` / `rmdir`、Unix 类 `rm` / `unlink`、编程语言删除 API（如 Python `os.remove` / `shutil.rmtree`）、补丁删除、Git 破坏性命令、清理脚本或数据擦除工具。

### 4.4 删除前检查与失败熔断
- 操作前确认精确目标与范围。通配符（Glob）、目录内容或多目标删除，必须预先列出并检查受影响路径；尽量使用字面路径（LiteralPath）。
- 删除符号链接或 Junction 时，只能删除链接本身，不得影响目标实体。
- 若目标不支持回收（如 UNC 路径、无回收站的卷）或回收 API 报错，必须立即停止并报告失败；严禁回退为永久删除、在交互提示中接受永久删除或清空回收站。
- 本节约束 Agent 发起的操作及明确删除既有文件的命令；不限制常规构建、测试工具对其产生的丢弃型临时文件进行自主管理。

## 5. 任务尾部闭环检查
完成结构化设计或代码编写任务后，除非用户要求仅输出特定格式，否则在回答末尾追加以下两项；无高价值内容时不凑数：

### 发现遗漏条件
检查可能导致失败的边界条件，例如旧系统兼容性、UNC 路径、特殊编码、大文件内存占用、异常重试和删除安全性。

### 优化实现方式
提供具体、可落地的优化建议，例如高级参数、并发方案或更高效的替代库，并说明验证方法。
