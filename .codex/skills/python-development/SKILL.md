# Python 开发规范

本 Skill 是 Python 程序在创建、修改、修复、优化时的统一开发规范。它不是 Python 教程；核心是指导 Agent 判断“什么时候做什么、为什么做、做到什么程度”。

三条最高原则始终遵守：

1. **宁可失败，不要猜。** 涉及删除、覆盖、移动、批量重命名、数据转换时，如果无法确认操作对象、范围、路径、格式或用途，不擅自扩大范围；必要时停止并说明缺失信息。
2. **最小必要修改。** 修改已有代码时，先阅读并理解现有结构，只修改完成任务所必需的部分，保留已有正确行为。
3. **先判断，再启用。** 不默认并发、重试、复杂架构或第三方库；方案规模应与任务规模、风险和实际瓶颈匹配，并遵循 `AGENTS.md` 的任务复杂度要求。

## 一、任务复杂度分级

完成任务前先判断复杂度，并据此决定工作方式。主要依据：影响范围、风险、数据规模、改动量、外部依赖以及验证难度。

- **简单任务**：单点改动、影响范围小、无明显外部依赖或数据风险。直接完成，进行必要的基本验证。
- **中等任务**：涉及已有流程、多文件、配置、并发或多个处理阶段，需要确认影响范围。先分析现有实现 → 针对性修改 → 验证核心功能。
- **复杂任务**：跨模块、大规模数据、外部程序、网络、打包、并发，或存在明显的数据覆盖/损坏风险。执行完整流程：
  1. 分析需求和现有代码。
  2. 明确成功标准和关键约束。
  3. 制定简短实现计划。
  4. 实施最小范围修改。
  5. 执行针对性验证。
  6. 根据验证结果修正实现。
  7. 报告实际修改和验证状态。

简单任务不要机械套用复杂流程；复杂任务也不要只修改后直接结束。

## 二、任务类型

### 新建

从零创建 Python 程序时，遵循完整规范，并按第五节的独立脚本约定建立基础结构。

如果存在：

```text
assets/template.py
````

优先读取并基于模板修改，不要从空文件重新实现模板已有的公共结构。

### 修改

修改已有脚本时：

* 首先阅读相关代码、配置以及必要的调用关系。
* 理解输入、处理流程和输出。
* 尽量局部修改。
* 不无理由重写整个文件。
* 不无理由更换第三方库、配置格式、日志结构或输出格式。
* 修改后验证新增功能以及受影响的原有功能。

### 修复 Bug

遵循：

```text
复现/收集错误
→ 定位原因
→ 最小修复
→ 验证
```

不要通过大量修改代码“碰运气”。

### 优化

遵循：

```text
测量
→ 定位瓶颈
→ 优化
→ 验证
```

没有证据证明存在性能问题时，不要为了“优化”而增加复杂并发或重构。

## 三、开发前的决策检查

根据任务实际情况判断以下问题：

1. 数据规模：文件数、单文件大小、总数据量。
2. 主要瓶颈：CPU、内存、磁盘、网络、文件系统、外部程序或 Python 本身。
3. 是否调用外部程序。
4. 是否涉及网络、UNC 或 SMB。
5. 是否可能出现临时性错误。
6. 是否需要并发。
7. 如果并发，线程还是进程。
8. 是否需要重试。
9. 是否需要 timeout。
10. 是否需要断点或失败恢复。
11. 是否需要日志。
12. 是否需要资源清理。
13. 是否需要特殊 Windows 处理。
14. 是否需要 PyInstaller / EXE 兼容。
15. 是否存在数据损坏、误修改、覆盖或重复处理风险。
16. 是否存在内存峰值风险。
17. 是否需要测试，以及测试到什么程度。

这些是**决策项，不是必须全部启用的功能**。

## 四、按需执行规则

### 4.1 并发

首先判断任务属于 I/O-bound、CPU-bound、memory-bound、disk-bound、network-bound 还是 external-process-bound。

#### I/O-bound

大量文件读写、网络文件、UNC、SMB、等待外部 I/O 等场景，可以考虑：

```python
ThreadPoolExecutor
```

并发数必须有界。

不要无限创建线程。

#### CPU-bound

图像计算/转换、压缩、OCR 后处理、CPU 密集型 PDF 或其他计算密集任务，可以考虑：

```python
ProcessPoolExecutor
```

或：

```python
multiprocessing
```

在选择之前考虑：

* CPU 核心数。
* 单任务耗时。
* 任务数量。
* 进程创建成本。
* 参数和结果的 pickle / serialization 成本。
* 内存占用。
* 磁盘竞争。
* 第三方库是否适合多进程。

CPU-bound 并不意味着一定需要多进程。如果单任务很轻、任务数量很少或进程管理成本明显，顺序执行可能更合适。

#### 外部程序

调用 ABBYY、Photoshop、Acrobat、ffmpeg、7-Zip、robocopy 等外部程序时使用：

```python
subprocess
```

并根据实际情况考虑：

* timeout。
* returncode。
* stdout / stderr。
* 有界并发。
* 重试。
* 子进程退出和资源清理。

如果外部程序自身已经具备较高并行能力，不要盲目叠加 Python 并发。

#### 小任务

任务数量少、单任务耗时很短，或者并发管理成本可能超过收益时，优先顺序执行。

**不要因为“任务很多”就自动使用多线程或多进程。**

### 4.2 Retry

先判断错误是：

```text
transient error
```

还是：

```text
permanent error
```

典型可重试情况：

* 网络临时断开。
* UNC 暂时不可访问。
* 文件暂时被其他程序占用。
* 某些临时 I/O 错误。
* 外部程序临时启动失败。
* timeout。
* 服务暂时不可用。

典型不可重试情况：

* 参数错误。
* 文件格式损坏。
* 数据本身无效。
* 路径明确不存在。
* 权限不足。
* 不支持的格式。
* Python 编程错误。
* 明确的逻辑错误。

原则：

```text
临时性失败 → 有限重试
确定性失败 → 尽快失败并报告原因
```

Retry 至少明确：

* 最大尝试次数。
* 等待间隔。
* 哪些异常可以重试。
* 操作是否幂等。
* 最终失败如何记录。
* 是否需要 cleanup。

必要时使用 exponential backoff。

默认：

```text
RETRY_COUNT = 3
RETRY_INTERVAL = 5
```

可以作为文件/网络类操作的合理起点，但不是所有任务的强制值，应根据任务特征调整。

禁止：

```python
except Exception:
    pass
```

也禁止对所有异常无条件 retry。

### 4.3 Retry 与幂等性

增加 retry 前必须考虑操作在失败后是否可能已经部分成功。

读取、检查和重新生成独立临时输出通常比较容易安全重试。

对于：

* 移动。
* 删除。
* 覆盖。
* 数据库写入。
* 向外部系统提交数据。
* 其他具有副作用的操作。

如果无法确认上一次操作是否已经成功，不要简单重复执行。

应先检查当前状态，避免：

* 重复处理。
* 重复写入。
* 数据丢失。
* 文件损坏。

### 4.4 Timeout

所有可能无限等待的操作都应判断是否需要 timeout，例如：

* subprocess。
* 网络请求。
* 外部程序。
* IPC。
* 可能阻塞的 I/O。

timeout 发生后：

```text
记录日志
→ 尝试安全终止/清理
→ 根据错误类型判断是否 retry
```

不要让单个异常任务无限阻塞整个批处理流程。

但对于无法可靠设置 timeout 的普通本地文件操作，不要为了形式而增加没有实际意义的 timeout。

### 4.5 Windows / multiprocessing / PyInstaller

涉及 multiprocessing 或打包 EXE 时必须检查：

```python
if __name__ == "__main__":
```

Windows 使用 `spawn` 时，特别注意：

* worker 可以被子进程正常导入。
* 不在模块 import 阶段创建进程。
* 必要时使用 `multiprocessing.freeze_support()`。
* 子进程数量受控。
* 避免 EXE 递归启动自身。
* 检查 PyInstaller 打包后的行为。

需要同时验证：

```text
.py
.exe
```

在以下方面是否一致：

* 脚本/EXE 所在目录。
* 同目录 INI。
* 日志。
* 临时目录。
* subprocess。
* multiprocessing。
* 第三方库资源。

### 4.6 文件安全

优先使用：

```python
pathlib.Path
```

并明确区分：

```text
输入路径
输出路径
临时路径
```

默认不要修改用户原始输入文件，除非需求明确要求。

涉及：

* delete
* overwrite
* move
* rename
* batch rename

必须确认操作对象和范围。

无法确认时：

```text
不要猜
不要扩大范围
必要时询问
```

写入已有重要文件时，必要时采用：

```text
临时文件
→ 完成写入
→ 验证
→ replace
```

而不是在验证之前直接破坏原文件。

### 4.7 临时文件

临时文件应：

* 使用明确的临时目录。
* 使用唯一名称。
* 与最终输出区分。
* 正常完成后清理。
* 异常时尽可能清理。

**只能清理当前任务明确创建的临时文件。**

禁止根据：

* 文件名看起来像临时文件。
* 修改时间。
* 扩展名。
* “应该已经没用了”。

来删除文件。

无法确认某文件是否由当前任务创建时，不删除。

### 4.8 防止重复处理

批处理程序需要判断任务是否可能被重复执行。

尤其是：

* retry。
* 程序中途崩溃后重新运行。
* 多线程/多进程。
* 输出文件已经存在。

必要时设计：

* 输出存在检查。
* 临时输出。
* 原子替换。
* 状态记录。
* 文件完整性检查。
* 可恢复处理。

不要简单通过“输出文件存在”就判断任务一定成功，也不要因为输出不存在就认为之前没有产生部分结果。

### 4.9 图像处理

使用 Pillow 等处理图像时，根据任务检查：

* 尺寸。
* DPI。
* 色彩模式。
* 位深。
* 压缩方式。
* 元数据。
* alpha。
* 文件格式。
* 内存占用。

批量处理时进一步判断：

```text
文件数量
单张大小
CPU 计算量
磁盘吞吐
输入/输出是否位于不同磁盘
网络
内存峰值
```

然后选择：

```text
顺序
ThreadPoolExecutor
ProcessPoolExecutor
```

不要默认 Pillow 使用线程一定更快。

大量图片并发处理时尤其注意：

```text
worker 数量 × 单任务内存
```

避免同时打开过多大型图片。

处理完成后及时释放 Image 和文件资源。

### 4.10 PDF 处理

使用 PyMuPDF、pikepdf、img2pdf 等处理 PDF 时，根据任务检查：

* 页数。
* 文件大小。
* 图像数量。
* 内存占用。
* 临时文件。
* 输出完整性。
* 是否覆盖源文件。
* DPI。
* MediaBox / CropBox。
* 元数据。
* 书签。
* 文字/图像内容。

大型 PDF 不要默认一次性全部加载到内存。

生成 PDF 后，在条件允许时重新打开或执行针对性验证，确认文件确实可用。

错误日志应至少能够定位：

```text
具体文件
→ 处理阶段
→ 具体异常
```

### 4.11 外部程序

调用外部 EXE 时必须检查：

```text
command
returncode
stdout
stderr
timeout
```

根据具体程序判断 `returncode != 0` 是否必然代表失败。

不要仅因为 subprocess 没有抛出 Python 异常，就认为外部程序执行成功。

如果外部程序可能产生部分输出，失败后必须考虑这些输出是否可继续使用、需要验证还是应该清理。

### 4.12 日志

新建独立工具默认使用：

```python
logging
```

至少区分：

```text
INFO
WARNING
ERROR
```

批处理程序发生失败时，应尽量记录：

```text
文件
操作
处理阶段
尝试次数
异常原因
```

subprocess 失败时，必要时记录：

```text
returncode
stderr
```

已有脚本存在日志系统时优先沿用，不要为了修改一个功能而无理由重写 logging。

### 4.13 资源管理

优先使用 `with` 确保异常情况下释放资源，例如：

* `open`。
* `Image.open`。
* executor。
* 临时目录。
* 网络连接。
* subprocess 相关资源。

对于需要显式关闭的 PDF、图像、进程等对象，必须确认生命周期。

不要因为使用上下文管理器就忽略对象之间的依赖关系。

### 4.14 配置

长期运行、批处理或 EXE 部署时，可以将真正需要用户调整的参数配置化，例如：

```text
输入路径
输出路径
THREAD_COUNT
RETRY_COUNT
RETRY_INTERVAL
TIMEOUT
```

不要为了“配置化”把所有内部常量都暴露给用户。

新建独立脚本的配置约定见第五节。

### 4.15 编码

文本读取优先考虑：

```text
UTF-8
```

涉及旧 Windows / 中文本地文件时考虑：

```text
GB2312 / GBK
```

读取失败时是否 fallback 应根据数据来源决定。

不要使用：

```python
errors="ignore"
```

来掩盖未知编码问题，因为这可能静默丢失数据。

写文件必须明确指定 encoding。

### 4.16 第三方依赖

标准库优先。

只有当第三方库能够明显提升：

* 功能。
* 稳定性。
* 性能。
* 可维护性。

时才引入。

例如：

```text
Pillow
PyMuPDF
pikepdf
openpyxl
pandas
```

引入第三方库时考虑：

* 实际用途。
* 版本兼容。
* 是否需要固定版本。
* PyInstaller 兼容性。
* EXE 打包额外处理。

不要为了简单功能引入过多依赖。

### 4.17 性能

性能优化遵循：

```text
测量
→ 定位瓶颈
→ 优化
→ 验证
```

重点判断：

```text
CPU
RAM
disk read
disk write
network
filesystem metadata
external process
serialization
```

不要默认：

```text
多线程一定更快
多进程一定更快
asyncio 一定更快
batch 一定更快
```

例如：

* CPU 已经饱和 → 增加线程通常不会解决 CPU 瓶颈。
* 磁盘已经达到吞吐上限 → 增加并发可能没有收益。
* 网络带宽已经达到上限 → 增加线程通常不能突破带宽限制。
* 大量小文件 → 适度并发可能有效。
* 大量 CPU 密集任务 → 可以考虑多进程。
* 大量数据需要进程间传输 → 必须考虑 serialization 成本。

如果没有实际测量条件，应明确说明性能判断属于估计，不要伪造 benchmark 结果。

### 4.18 测试与验证

验证程度根据任务风险决定。

#### 小型修改

至少考虑：

* 语法检查。
* import。
* 关键路径运行。

#### 文件批处理

至少测试：

* 正常输入。
* 异常输入。
* 输出结果。
* 重试行为。
* 源文件未被意外修改。

#### 并发

至少检查：

* worker 数。
* 所有任务是否完成。
* 异常是否传播。
* 是否存在丢失/重复处理。
* 资源是否释放。

#### multiprocessing

检查：

* Windows 启动。
* worker 启停。
* main guard。
* `freeze_support()` 是否需要。
* PyInstaller 行为。

#### 图像 / PDF

检查：

* 输出是否可以重新打开。
* 尺寸。
* 页数。
* DPI。
* 格式。
* metadata。
* 内容完整性。

测试重点不是证明“程序没有报错”，而是确认：

```text
输出结果正确
```

### 4.19 失败恢复与断点

当任务具有以下特征时，判断是否需要恢复机制：

* 文件数量非常大。
* 单个任务耗时很长。
* 外部程序运行时间长。
* 网络不稳定。
* 任务可能运行数小时。
* 中途失败会导致大量重复处理。

可以考虑：

```text
已完成记录
输出状态
临时文件
阶段状态
重新运行时跳过已确认完成任务
```

但小型一次性任务不需要为了断点恢复增加复杂状态系统。

恢复机制必须以“能够确认任务确实完成”为前提，不要仅凭文件存在判断成功。

### 4.20 数据验证

对于文件转换、复制、生成 PDF、图像处理等任务，不能只验证：

```text
程序返回成功
```

必要时验证：

* 文件存在。
* 文件大小合理。
* 文件可以重新打开。
* 页数 / 尺寸正确。
* 内容数量正确。
* checksum / hash。
* 输出与输入的对应关系。
* 是否存在 0 字节或明显不完整文件。

验证方式应与数据类型和任务风险匹配。

## 五、新建独立脚本的脚手架约定

从零编写需要交付为独立程序（常为单文件 EXE）的脚本时，遵循以下约定，保证直接运行 `.py` 与打包后的 EXE 行为一致。

### 1. 路径兼容

使用 `sys.frozen` 判断运行环境：

* `.py`：使用 `__file__` 所在目录。
* PyInstaller EXE：使用 `sys.executable` 所在目录。

需要读取脚本同级文件时，以该目录为基准，不依赖当前工作目录。

### 2. INI 配置

配置文件默认使用与脚本同名的：

```text
脚本名.ini
```

使用 `configparser`，读写明确指定：

```text
encoding="gb2312"
```

配置文件不存在时，根据程序需求创建并停止运行；配置项使用中文注释。

### 3. 默认并发与重试

新建批处理工具默认：

```text
THREAD_COUNT = 1
```

文件/网络类可重试错误可以默认：

```text
RETRY_COUNT = 3
RETRY_INTERVAL = 5
```

但实际任务允许根据数据规模、网络环境和错误特征调整。

### 4. 依赖

标准库优先。

确有需要时再引入第三方库，并说明其用途。

### 5. 纯文本

txt、csv 等文本文件默认优先：

```text
UTF-8
```

如果数据来源明确存在旧 Windows 编码，再考虑：

```text
GB2312 / GBK
```

不要无条件假设所有文本都是 UTF-8，也不要通过 `errors="ignore"` 静默丢失字符。

### 6. 致命错误

独立 EXE 工具如果适合双击运行，应捕获无法继续的顶层异常，记录明确错误，并根据运行方式决定是否：

```python
input("按 Enter 键退出...")
```

不要对所有 Python 程序强制添加交互式暂停；例如由终端、其他程序或自动化系统调用时，应避免阻塞调用方。

### 7. 日志

新建独立批处理工具默认启用 `logging`。

如果项目采用双日志约定，则：

```text
{脚本名}_{时间戳}_info.log
{脚本名}_{时间戳}_error.log
```

分别记录 INFO 与 WARNING/ERROR。

日志：

```text
encoding = utf-8
format = %(asctime)s [%(levelname)s] %(message)s
timestamp = YYYYmmdd_HHMMSS
```

如果实际运行环境更适合单一日志文件，则可以根据任务需求调整，不要为了双日志而增加不必要的复杂度。

### 8. 模板

如果存在：

```text
assets/template.py
```

开始新建脚本前读取它。

如果模板已经包含：

* 路径处理。
* 配置读写。
* 日志。
* retry。
* I/O 线程池。
* 顶层异常处理。

应优先复用，而不是重新实现。

如果任务需要 `ProcessPoolExecutor` 或 multiprocessing，则根据第四节的 Windows 规则调整模板。

## 六、执行流程

根据任务实际复杂度执行：

```text
读取需求
→ 判断简单/中等/复杂
→ 判断新建/修改/修复/优化
→ 阅读相关代码和配置
→ 判断数据规模
→ 判断 CPU / I/O / memory / disk / network / external-process 特征
→ 判断外部程序、网络、UNC
→ 判断 retry / timeout / concurrency / recovery
→ 判断文件安全与资源生命周期
→ 判断 Windows / PyInstaller
→ 实现最小必要修改
→ 验证
→ 根据验证结果修正
→ 报告实际修改和验证结果
```

不要求将全部决策过程输出给用户。

简单任务可以直接执行；只有复杂任务才需要完整计划。

遇到不确定：

```text
检查 → 验证 → 必要时询问
```

涉及删除、覆盖、移动、批量修改或高风险数据转换时：

```text
无法确认 → 不执行
```

## 七、最终原则

始终优先考虑：

```text
正确性
→ 数据安全
→ 可恢复性
→ 可验证性
→ 稳定性
→ 性能
→ 代码简洁
```

不要为了性能牺牲数据正确性，也不要为了“工程完整”引入任务实际不需要的复杂度。
