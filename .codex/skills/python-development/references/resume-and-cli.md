# 断点续传、运行前确认与命令行参数

适用范围：批处理或长时间运行的脚本需要判断「哪些任务已经完成」、需要支持中途失败后继续处理、需要交互确认，或需要被自动化调用时使用。临时文件、安全写入与删除边界见 `references/data-integrity.md`。

## 是否值得支持断点续传

用户没有明确要求「断点续传」时，不要直接假设一种固定实现方式。应在方案设计阶段判断该项目是否值得支持，并向用户说明推荐方案与理由。

- 小型一次性任务、单任务耗时短、重复处理代价低时，不必为断点续传增加复杂度。
- 文件数量大、单任务耗时长、外部程序运行时间长、网络不稳定、中途失败会导致大量重复处理时，才值得支持。
- 采用哪种方案、为什么采用，必须在写代码前说明，不要等实现完成后补。

## 「已完成」判定

优先选择能够直接验证最终结果的方式，避免仅依赖「程序曾经运行过」作为完成依据：

- 目标文件存在且文件大小 > 0；
- 页数/尺寸正确、文件数量正确、文件结构正确；
- PDF 可正常打开，且页面数量与输入一致；
- 输出文件满足项目要求（格式、命名、内容数量、必要校验信息等）。

仅凭「输出文件存在」不足以判定成功；也不要因为输出不存在就认为之前没有产生部分结果。

## 状态记录文件

只有当项目本身存在中间阶段、批量任务状态复杂，或无法可靠通过最终产物判断时，才建立状态记录文件，例如脚本文件所在目录的 JSON。

状态文件应记录：已处理文件、已完成任务、失败任务、当前处理阶段、必要的校验信息。但不能机械要求所有项目都使用 JSON；SQLite、目标文件校验或其他等效方式都可以，按项目实际情况选择。

能够通过目标文件可靠判断处理完成时，不要额外建立状态数据库或复杂状态文件。

## 运行前确认

适用于实现了断点续传或已处理状态判断，或运行时存在「继续执行现有任务」行为的脚本。纯库代码、不适合交互的调用场景不强行加入。

正式开始处理前提示当前状态并请求确认，例如：

```text
检测到已有处理记录 / 已存在部分输出文件。
程序将跳过已经完成的项目并继续处理。
是否继续？[Y/N]
```

具体提示内容根据项目实际逻辑设计，不要求固定文案。

## 命令行参数

此类脚本必须支持命令行参数，以便自动化运行或绕过交互确认。

### 强制全部重新生成

```text
--force
```

语义：忽略已有状态、忽略「已处理」判断，按项目定义重新生成全部目标。

不要仅删除状态文件来实现「强制重新生成」，应由程序显式控制重新处理逻辑；这样即使断点记录从 JSON 换成 SQLite、目标文件校验或其他方式，命令语义仍然稳定。

### 跳过运行确认

```text
--yes
```

或：

```text
--no-confirm
```

语义：不显示交互确认，直接开始运行。参数名可根据现有脚本风格选择，但必须做到：

```text
正常运行：默认可以进行确认
自动化运行：支持参数跳过确认
完整重建：支持参数强制重新生成
```

`--force` 管处理范围，跳过确认参数管是否交互，二者语义正交，可以组合使用（例如无人值守的全量重建）。

命令行参数应使用标准库 `argparse`，除非项目存在明确理由采用其他方案。同一个脚本里的确认逻辑与命令行参数应保持一致。
