# 断点续传、失败清单与命令行参数

适用范围：批处理或长时间运行的脚本需要判断「哪些任务已经完成」、需要支持中途失败后继续处理、需要交互确认，或需要被自动化调用时使用。临时文件、安全写入、UNC 与删除边界见 `references/data-integrity.md`。

## 是否值得支持断点续传

用户没有明确要求「断点续传」时，不要直接假设一种固定实现方式。应在方案设计阶段判断该项目是否值得支持，并向用户说明推荐方案与理由。

- 小型一次性任务、单任务耗时短、重复处理代价低时，不必为断点续传增加复杂度。
- 文件数量大、单任务耗时长、外部程序运行时间长、网络不稳定、中途失败会导致大量重复处理时，才值得支持。
- 采用哪种方案、为什么采用，必须在写代码前说明，不要等实现完成后补。

## 「已完成」判定

优先选择能够直接验证最终结果的方式，避免仅依赖「程序曾经运行过」作为完成依据：

- 目标文件存在且文件大小 > 0；
- 页数/尺寸正确、文件数量正确、文件结构正确；
- PDF 可正常打开，且页面数量与输入一致；
- 输出文件满足项目要求（格式、命名、内容数量、必要校验信息等）。

仅凭「输出文件存在」不足以判定成功；也不要因为输出不存在就认为之前没有产生部分结果。

## 状态记录文件

只有当项目本身存在中间阶段、批量任务状态复杂，或无法可靠通过最终产物判断时，才建立状态记录文件，例如脚本文件所在目录的 JSON。

状态文件应记录：已处理文件、已完成任务、失败任务、当前处理阶段、必要的校验信息。但不能机械要求所有项目都使用 JSON；SQLite、目标文件校验或其他等效方式都可以，按项目实际情况选择。

能够通过目标文件可靠判断处理完成时，不要额外建立状态数据库或复杂状态文件。

## 失败清单（批处理默认产出）

批处理工具失败时不能只在日志里写一行，要产出可被程序直接消费的失败清单：

```text
failed_YYYYmmdd_HHMMSS.csv
```

约定：

- 与脚本/EXE 放在同一目录（程序所在目录，不是当前工作目录）；
- 列固定为四列：`原路径`、`失败阶段`、`异常摘要`、`是否可重试`；
- 编码 `utf-8-sig`，Excel 双击打开不乱码；
- 没有失败时不生成文件（避免堆一堆空文件）；
- `原路径` 必须是能直接回灌给下次运行的原始输入路径；
- 退出码：`0` 全部成功、`1` 致命错误（无法继续）、`2` 部分任务失败。自动化脚本应据此判断，而不是只看日志。

模板对应：`FailureRecord`、`write_failure_report()`、`latest_failure_report()`、`load_failure_report()`、退出码常量 `EXIT_OK / EXIT_FATAL / EXIT_PARTIAL_FAILURE`。

## 二次运行：--only-failed

```text
--only-failed
```

语义：忽略常规输入枚举，直接读取失败清单的 `原路径` 列，只处理这些文件。默认取程序目录下最新的 `failed_*.csv`，可用 `--failure-report <路径>` 指定具体清单。

与 `--force` 的关系（两者正交，可组合）：

| 参数 | 管什么 |
| --- | --- |
| `--force` | 处理范围：忽略「已完成」判定与断点状态，重新生成全部目标 |
| `--only-failed` | 输入来源：只处理失败清单里的目标 |
| `--yes` / `--no-confirm` | 是否交互：跳过运行前确认 |
| `--failure-report` | 指定使用哪一份失败清单 |

`--force --only-failed` 表示：对失败清单里的目标忽略「已完成」判定，全部重新处理。

注意：`--only-failed` 不能替用户猜失败清单的位置；找不到清单时直接报错退出（退出码 1），不要静默改成全量处理。

## 运行前确认

适用于实现了断点续传或已处理状态判断，或运行时存在「继续执行现有任务」行为的脚本。纯库代码、不适合交互的调用场景不强行加入。

正式开始处理前提示当前状态并请求确认，例如：

```text
检测到已有处理记录 / 已存在部分输出文件。
程序将跳过已经完成的项目并继续处理。
是否继续？[Y/N]
```

具体提示内容根据项目实际逻辑设计，不要求固定文案。

非交互环境（无 tty，例如被其他程序调用）不应阻塞等待输入：模板 `confirm()` 在无 tty 时记录日志后继续，自动化场景请显式传 `--yes`。

## 命令行参数

此类脚本必须支持命令行参数，以便自动化运行或绕过交互确认。

### 强制全部重新生成

```text
--force
```

语义：忽略已有状态、忽略「已处理」判断，按项目定义重新生成全部目标。

不要仅删除状态文件来实现「强制重新生成」，应由程序显式控制重新处理逻辑；这样即使断点记录从 JSON 换成 SQLite、目标文件校验或其他方式，命令语义仍然稳定。

### 跳过运行确认

```text
--yes
```

或：

```text
--no-confirm
```

语义：不显示交互确认，直接开始运行。参数名可根据现有脚本风格选择，但必须做到：

```text
正常运行：默认可以进行确认
自动化运行：支持参数跳过确认
完整重建：支持参数强制重新生成
失败重跑：支持参数只处理失败项
```

命令行参数应使用标准库 `argparse`，除非项目存在明确理由采用其他方案。同一个脚本里的确认逻辑与命令行参数应保持一致。模板中已给出 `build_arg_parser()`，直接复用而不是另起一套命名。
