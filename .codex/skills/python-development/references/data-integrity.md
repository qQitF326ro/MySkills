# 数据完整性与文件安全

适用范围：涉及文件的读取、写入、转换、覆盖、临时文件、批量处理、失败恢复与结果校验时使用。

## 路径与资源

优先使用 `pathlib.Path`，明确区分输入路径、输出路径、临时路径，三者不要混用。默认不修改用户原始输入文件；只有需求明确要求修改、覆盖、移动或删除输入文件时才允许。

文件和外部资源优先使用 `with`，确保异常发生时能够释放：`open`、`Image.open`、executor、临时目录、`subprocess`、网络连接。

但使用上下文管理器不代表资源生命周期问题已经解决。PDF/图像对象、进程、subprocess 以及依赖其他对象生命周期的资源，必须确认对象之间的依赖关系与关闭顺序，避免这类隐蔽错误：对象 A 依赖对象 B，先关闭 B，之后仍继续使用 A。

## 临时文件与安全写入

临时文件必须使用明确的临时目录与唯一文件名，与最终输出文件明确区分，避免直接在最终输出路径上做不完整写入，正常与异常结束时都尽可能清理。

写入已有重要文件时按以下顺序执行：

```text
创建临时目录
    ↓
创建唯一临时文件
    ↓
完整写入
    ↓
验证临时文件
    ↓
替换正式文件
```

例如使用 `Path.replace()`，或项目中更合适的原子替换方式。不允许对重要目标文件采用「直接打开目标文件 → 覆盖 → 最后才验证」。核心要求：在新文件没有完成并验证之前，不要破坏原来的重要文件。

## 防止重复处理

批处理需判断任务是否可能被重复执行，尤其是 retry、中途崩溃后重跑、多线程/多进程、输出文件已存在。必要时设计：输出存在检查、临时输出、原子替换、状态记录、文件完整性检查、可恢复处理。不要简单通过「输出文件存在」判断成功，也不要因为输出不存在就认为之前没有部分结果。

## 失败恢复与断点

当文件数非常大、单任务耗时长、外部程序运行时间长、网络不稳定、中途失败会导致大量重复处理时，考虑已完成记录、输出状态、阶段状态，并在重新运行时跳过已确认完成的任务。小型一次性任务不需要为此增加复杂状态系统。

恢复机制必须以「能确认任务确实完成」为前提，不要仅凭文件存在判断成功。是否值得支持断点续传、如何定义「已完成」、状态记录文件如何设计，以及运行前确认与命令行参数，见 `references/resume-and-cli.md`。

## 删除边界

只能清理当前任务明确创建的临时文件 / 临时目录。

严格禁止根据以下理由自行删除文件：文件名看起来像临时文件、修改时间比较久、扩展名看起来不重要、文件大小异常、「应该没用了」、「应该是上一次留下的」、「看起来就是程序产生的」。

如果无法确认文件属于当前任务创建的临时文件，不要删除；宁可保留并报告。

## 数据验证

对文件转换、复制、生成 PDF、图像处理等，不能只验证程序返回成功。必要时验证：文件存在、大小合理、可重新打开、页数/尺寸正确、内容数量正确、checksum/hash、输出与输入的对应关系、是否存在 0 字节或明显不完整文件。验证方式应与数据类型和任务风险匹配。测试重点不是证明「程序没报错」，而是确认输出结果正确。
