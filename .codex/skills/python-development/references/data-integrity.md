# 数据完整性与文件安全

适用范围：涉及文件的读取、写入、转换、覆盖、临时文件、批量处理、失败恢复与结果校验时使用。

## 路径与资源

优先使用 `pathlib.Path`，明确区分输入路径、输出路径、临时路径。默认不修改用户原始输入文件，除非需求明确要求。优先使用 `with` 确保异常时释放 `open`、`Image.open`、executor、临时目录、网络连接、subprocess 相关资源。需要显式关闭的 PDF、图像、进程等对象必须确认生命周期；不要因为使用上下文管理器就忽略对象间依赖。

## 临时文件与安全写入

临时文件应使用明确临时目录、唯一名称、与最终输出区分，正常与异常时都尽可能清理。写入已有重要文件时采用：临时文件、完整写入、验证、`replace`，而不是在验证前直接破坏原文件。只能清理当前任务明确创建的临时文件。禁止根据文件名像临时文件、修改时间、扩展名或「应该没用了」来删除文件。无法确认归属时不删除。

## 防止重复处理

批处理需判断任务是否可能被重复执行，尤其是 retry、中途崩溃后重跑、多线程/多进程、输出文件已存在。必要时设计：输出存在检查、临时输出、原子替换、状态记录、文件完整性检查、可恢复处理。不要简单通过「输出文件存在」判断成功，也不要因为输出不存在就认为之前没有部分结果。

## 失败恢复与断点

当文件数非常大、单任务耗时长、外部程序运行时间长、网络不稳定、任务可能运行数小时、中途失败会导致大量重复处理时，考虑已完成记录、输出状态、临时文件、阶段状态、重新运行时跳过已确认完成任务。小型一次性任务不需要为此增加复杂状态系统。恢复机制必须以「能确认任务确实完成」为前提，不要仅凭文件存在判断成功。

## 数据验证

对文件转换、复制、生成 PDF、图像处理等，不能只验证程序返回成功。必要时验证：文件存在、大小合理、可重新打开、页数/尺寸正确、内容数量正确、checksum/hash、输出与输入的对应关系、是否存在 0 字节或明显不完整文件。验证方式应与数据类型和任务风险匹配。测试重点不是证明「程序没报错」，而是确认输出结果正确。
