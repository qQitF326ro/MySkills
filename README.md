### 1. 调查结论

Codex 与普通聊天模型不同：它能读文件、执行命令、改代码、运行测试，因此 Prompt 的核心不是“教它思考”，而是“说明任务边界和完成状态”。

最重要的结论如下：

- OpenAI Codex 官方最佳实践推荐的 Prompt 骨架是：目标、上下文、约束、完成标准。这个结论与 DeepSeek V4 资料中“编码 Agent 模板”的结构基本一致。
- Codex 在“代码可验证”时结果更好。因此应该给出复现步骤、测试命令或可观察的验收条件，而不是只写“帮我优化一下”。
- 对已有代码，Codex 的默认行为是“最小改动、保持现有结构”；对全新任务，官方系统提示词允许更有创造力和更大自由度。所以用户 Prompt 应该区分“修改”和“新建”。
- 复杂、模糊或多阶段任务应先计划。OpenAI 官方建议使用 `/plan` 或先让 Codex 调研、提问，而不是直接开始大规模改动。
- DeepSeek 提示资料中最适合 Coding Agent 的是“直接写目标与验收、不要要求逐步思考、少用示例、关键约束放用户消息、任务里给报错原文和文件”。不适合的是角色扮演式身份、思考过程指令、公文/角色生成类模板。
- awesome-deepseek-prompts 是聚合资料，不是权威来源。里面有价值的只有 V4 提示指南和 DeepSeek 官方引用；其余角色扮演、公文写作、jailbreak 内容不应进入编程 Agent 规范。
- 不需要在 Prompt 中重复 Codex 已经具备的能力。例如“请先搜索代码”“请逐步执行”“请运行命令后继续修改”这类话通常没有价值，因为 Codex 本身就是这样一个执行循环。

### 2. 推荐的核心 Prompt 模型

```text
目标：<你要实现、修改、排查或分析什么>
上下文：<相关文件 @path / 当前行为 / 报错 / 复现方式>
约束：<可改范围、禁止事项、必须保留的行为或接口>
成功标准：<测试、命令、输出结果或可观察条件>
```

字段规则：

- `目标`：必须有。要具体到“当前是什么、要变成什么”，不要只写“让代码更好”。
- `上下文`：修改或分析时通常有。不需要粘贴大段代码，Codex 能自己读文件；直接用 `@path` 指向文件，或给报错和复现步骤。
- `约束`：不总是需要，但修改已有代码时通常需要。只写真正会影响执行的内容，例如“不改接口”“不要动配置格式”“不要碰 `tools/` 目录”。
- `成功标准`：改动、重构、Bug 修复时尽量有。可以是命令通过、行为不再复现、输出文件内容正确、diff 只包含目标文件。
- `非目标`：复杂或高风险任务再加，例如“本次不做性能优化”“不要迁移现有配置”。

最少告诉 Codex 的只有三件事：要什么、哪里相关、怎样算完成。实现细节多数应该由 Codex 自己决定。

### 3. Codex 长期使用 Prompt 规范

以下模板不重复全局 `AGENTS.md` 中已有的语言、文件安全、验证原则。模板只在需要时填写字段。

**① 分析已有 Python / AHK 代码**

```text
分析 @<path> 的 <目标区域/流程>。

需要回答：
1. 入口、主流程、数据流和关键函数职责。
2. 关键边界条件、异常、编码/路径/资源风险。
3. 如果要修改 <目标>，真正相关的位置和影响面。

约束：
- 只读分析，不修改文件，不创建文件。
- 信息不足时列出缺口，不要猜测。

完成标准：结论可以定位到具体文件或函数。
```

**② 修改单个功能**

```text
修改 @<path> 中的 <函数/功能>。

当前行为：<一句话>
目标行为：<一句话>

约束：
- 修改范围：<允许改动的文件或函数>
- 保留：<现有接口/日志格式/输出格式/其他行为>
- 不要修改：<无关文件或功能>

成功标准：
- <测试或检查命令> 通过；
- <最小验证方式> 后得到 <期望结果>。

完成后报告改动文件、验证命令和实际结果。
```

**③ 新增脚本**

```text
使用 $python-development 创建 <目标脚本路径>；如果是 AHK，创建后执行 $ahk-load-check。

用途：<一句话>
输入：<路径、参数、配置或交互方式>
输出：<文件、日志、返回值或界面行为>

必要要求：
- <核心功能 1>
- <核心功能 2>

不需要：<明确不做的事情>

成功标准：
- <最小运行示例> 成功；
- 输出内容符合预期；
- Python 脚本在 `.py` 和打包后 `.exe` 路径模式下都验证通过。
```

**④ 重构**

```text
重构 @<path/区域>，提升 <可读性/结构/可维护性>，不改变 <行为/公开接口/输出格式>。

约束：
- 不做无关修复；
- 不无理由更换依赖或输出格式；
- 不重写 <用户指定的部分>。

工作方式：
- 先梳理当前结构和行为契约；
- 提出简短重构计划；
- 如果重构会改变行为，先停下说明。

成功标准：
- 重构前后对同一批样例输入产生一致结果；
- <lint/test 命令> 通过；
- diff 只包含计划内改动。
```

**⑤ Bug 排查**

```text
Bug：<症状>
复现步骤：
1. <step>
2. <step>

期望：<正确行为>
实际：<错误行为>
疑似相关：@<path>

约束：
- 先定位根因再做最小修复；
- 不修改无关功能；
- 不加临时绕过。

完成标准：
- 修复前复现问题；
- 修复后复现步骤不再触发；
- 相关检查或回归测试通过。

如果无法稳定复现，报告已知证据和下一步验证方法，不要靠猜。
```

**⑥ 复杂多步骤任务**

```text
目标：<最终成果和可验证终点>
上下文：<相关代码/仓库/外部系统/限制>
约束：<架构、依赖、范围、禁止事项>
非目标：<本次不做的事>

工作方式：
- 使用 /plan 或 /goal 把任务转成可验证的阶段；
- 先读相关代码并列出关键假设和缺口；
- 每个阶段完成后执行对应验证；
- 关键歧义影响实现时先询问，不要自行猜定。

成功标准：
- <阶段 1 验收>
- <阶段 2 验收>
- 最终结果可复现。
```

**⑦ 只分析不修改**

```text
只分析，不修改任何文件，不创建文件，不安装依赖，不运行有副作用的命令。

对象/问题：<要调查的代码、系统或设计>
需要判断：
- <问题 1>
- <问题 2>

输出要求：结论先行；说明证据和不确定性；不要给出修改后的代码。

完成标准：问题有明确结论或明确列出缺少的证据。
```

各场景的处理要点：

- ①⑦：只读，不需要代码测试；关键是输出结构和“不要猜”。
- ②：先读现有实现，单点改动通常不需要正式计划；验证新增行为和原有行为。
- ③：复用 Python / AHK Skill 中的长期规范；做语法、最小运行、路径兼容验证。
- ④：必须先理解行为契约；影响面稍大就要求先给计划。
- ⑤：必须复现或明确“无法复现”；修复后重新走复现步骤。
- ⑥：必须计划、分阶段、逐段验证；适合 `/plan` 或 `/goal`。

### 4. AGENTS.md / Skills / Prompt 的职责划分

| 层 | 应放什么 | 不应放什么 |
|---|---|---|
| 全局 `AGENTS.md` | 跨项目个人默认值：语言、回答风格、验证原则、文件与数据安全、Git 工作区保护、通用高风险命令规则 | Python/AHK 的具体技术规范、某仓库命令、某次任务目标 |
| 项目 `AGENTS.md` | 仓库布局、入口点、构建/测试/lint 命令、项目约定、必须保留的行为、禁止改动区、发布前验证方式 | 通用编程规则，重复全局规则，单次任务的验收 |
| Python / AHK Skill | 按语言或工作流可复用的方法：Python 开发规范、图像/PDF/OCR/并发/retry/日志、PyInstaller 处理、AHK 启动验证、模板和脚本 | 用户个人沟通偏好、跨语言通用文件安全原则、当前任务目标 |
| 当前 Prompt | 本次目标、当前状态、相关文件、本次约束、本次成功标准、本次输出要求 | 长期规则、完整领域手册、Agent 的基础执行能力说明 |

关于当前职责划分，注意几点：

- 全局 `AGENTS.md` 适合保持“行为基线”，不应把所有编码细节都放进去。
- `python-development` 这种 Skill 适合承载 Python 创建、修改、修复、打包、Windows 环境规范；AHK 已有 `ahk-load-check`，如果以后 AHK 开发变多，应扩展为一个通用 AHK 开发 Skill。
- Skill 只应在被触发时加载。官方文档明确 Skills 使用 progressive disclosure，初始只显示 `name`、`description` 和路径；完整内容在调用时才读取。所以描述要写清楚触发条件。
- 冲突优先级建议为：当前 Prompt 的明确指令 > 更接近当前目录的 `AGENTS.md` > 全局 `AGENTS.md`。Skill 只在符合其 `description` 时使用；如果某次任务不想用某个 Skill，应在当前 Prompt 中明确“忽略”它。
- 如果一个规则已经写进 `AGENTS.md` 或 Skill，就不要每次重复。只有当前 Prompt 要覆盖默认规则时才重复。

### 5. 常见错误

| 错误写法 | 为什么差 | 改进方式 |
|---|---|---|
| “帮我改一下代码” | 没有目标、范围、完成定义，Codex 只能猜 | 用“目标 + 约束 + 成功标准”三件套 |
| Prompt 很长且充满“你要小心、要专业、要逐步处理” | 消耗上下文，且多数是空泛规则 | 只保留事实性约束和验收；长期规则放入 `AGENTS.md` / Skill |
| “先把 A 函数改成 B，再改成 C，再删除 D” | 过度规定实现步骤，Codex 没有空间选择合理方案 | 说明结果和约束；只有架构决策才规定实现方式 |
| 没有禁止修改范围 | Codex 可能顺手重构、格式化或修无关问题 | 写清“只改 X，不要改 Y” |
| 没有验收标准 | 不知道何时结束，容易只做表面修改 | 给出命令、样例输出、行为不复现等可验证条件 |
| 只说“要新增功能”，不说现有行为 | Codex 可能破坏现有约定 | 修改前描述当前行为与目标行为 |
| 自己猜测“Bug 一定在 `xx.py` 第 100 行” | 如果猜错，会让 Codex 浪费时间和错误方向 | 给相关文件或症状，让 Codex 先验证位置 |
| 每次重复“Windows 注意 UNC、不要删文件、中文注释” | Prompt 膨胀；规则应该长期沉淀 | 写入全局或项目 `AGENTS.md` / Skill |
| “请一步一步思考”“请像专家一样回答” | 对 Coding Agent 通常无效，甚至浪费推理 | Codex 本身已有执行循环；只描述任务边界 |

### 6. 最终推荐模板

最终的最小通用模板是：

```text
<任务动词 + 明确对象>：<目标>

相关代码/当前行为/复现：@path / <一句话>

约束：<可改范围 / 禁止事项 / 必须保留>

成功标准：<命令、输出或行为条件>
```

使用示例：

```text
修改 @tool.py 中的图片尺寸判断逻辑。
当前行为：只处理 300 DPI。
目标行为：同时支持 300/600/150 DPI。
约束：只改该函数；保持 CSV 读取格式；不新增依赖。
成功标准：用样例图片运行后生成正确尺寸；脚本无语法错误。
```

如果你的任务只有一句话，例如“解释 `main()` 的流程”，不必强行套模板。模板的价值在于处理“需要 Codex 自主完成但结果必须可靠”的修改、重构、新建、排查和复杂任务。
